1 · Context04

Context

A hackathon touches a hundred small decisions — who may enter, who is on which team, who judges what, whose score counts. Run on forms and spreadsheets, each one is a place where the event loses time or loses trust.

Entry

Eligibility is manual

FPT students and external students enter through different doors, and someone has to verify each of them by hand.

Teams

Team-building is ad hoc

Size limits, one-team-per-event, invitations, join and leave requests — all tracked in chat threads.

Judging

Scoring is a spreadsheet

Weighted rubrics across several judges, with no conflict-of-interest check and no history of who changed what.

Results

Results are hard to defend

Judges disagree, ties happen at the cut-off, and teams have no channel to contest a score.

Framing derived from the business rules the system actually enforces (registration & verification, team constraints, conflict detection, deviation review, disputes, tie-break). No external market research was carried out for this project.

2 · Proposed Solutions05

Proposed Solutions

One platform covering the full lifecycle of an event, with the competition rules encoded in the backend rather than in a coordinator's head.

Pillar 01

Run the whole event

  • Event phases UPCOMING → OPEN → CLOSED_REGISTRATION → ACTIVE → SCORING → COMPLETED
  • Rounds (preliminary / final), tracks, schedule and milestone gates
  • Enrolment, magic-link registration, external-student verification
  • Team creation, invitations, join / leave requests, auto team matching
Pillar 02

Score it defensibly

  • Scoring templates and criteria whose weights must total 100%
  • Conflict-of-interest detection — a mentor cannot judge their own team
  • Automatic deviation review when judges disagree past a threshold
  • Weighted aggregation, tie-break, finalist selection, awards, disputes
Pillar 03

Keep it accountable

  • Five account types with method-level role checks on every endpoint
  • Append-only audit log — no update, no delete, exportable by admin
  • Domain events drive e-mail and in-app notifications
  • Live scoreboard and public event pages for spectators

2 · Proposed Solutions | Architecture07

System Architecture

A modular monolith: eleven business modules inside one deployable, isolated by Spring Modulith. Modules never touch each other's repositories or entities — only public service interfaces and domain events.

authJWT, refresh tokens, OTP, magic link, account locking
userSingle source of truth for accounts, approval, profiles
eventEvents, rounds, tracks, criteria, schedule, staff, awards
teamTeams, invitations, join/leave, matching, mentor chat
submissionVersioned submissions, attachments, deadline gates
judgingScores per criterion, conflicts, review, locking
rankingAggregation, finalists, results, disputes, season ranking
progressTeam progress tracking and risk flags
feedbackPost-event participant feedback
notificationE-mail + in-app, driven by domain events
auditAppend-only log, admin export
common / infrastructureBase entity, enums, config, SMTP sender
Synchronous — public service interfaces

A consumer injects *PublicService, never a repository or entity from another module. Boundaries are enforced by a Spring Modulith verification test.

Asynchronous — domain events

42 event types. Score changes trigger ranking recalculation; every mutation reaches the audit listener; selected events reach notifications.

2 · Proposed Solutions | Scoring Model08

Scoring & Ranking Model

How a set of judge opinions turns into a defensible ranking.

StageRule in the system
CriteriaWeights per round must sum to 100%; scoring templates are seeded and reusable.
EntryScore per criterion on the configured scale; a comment is mandatory for extreme scores.
ConflictA judge assigned as mentor to a team cannot score that team.
Deviationmax(percent) − min(percent) ≥ 25 opens a review request for the coordinator.
AggregateWeighted score per judge, then the mean across judges.
AdvancePER_TRACK_TOP_N for the preliminary round, FINALIST_POOL for the final.
PublishRankings are published by a coordinator; teams may dispute within the dispute window.
Deviation formula

weightedi = Σ (criterion × weight / 100)
percenti = weightedi × 20
deviation = max(percent) − min(percent)

One open review record per submission — the check is idempotent, and both creation and resolution are audited.

Contested slots

Ties are typed, not silent: PER_TRACK_CUTOFF when teams tie at the top-N line of a track, OVERFLOW_FILL when filling the remaining finalist slots.

Audit

The audit repository deliberately extends the bare Repository interface — there is no update or delete method to call. Export is admin-only and the export itself is logged.

Scheduled work

Two background schedulers run outside user requests: event maintenance (phase upkeep) and team progress evaluation, which raises AT_RISK and CRITICAL flags for mentors.

5 · Limitations20

Limitations

What the system does not do, stated from the state of the repository rather than from intent.

Technical
  • No deployment artefacts.There is no Dockerfile or compose file in the repository; the deployment guide still describes a PostgreSQL setup while the application runs on SQL Server with Flyway.
  • Local disk storage.Uploads are written under backend/uploads — no object storage, no CDN, and nothing shared between instances.
  • Single deployable, single database.The modular monolith gives clean boundaries but no independent scaling per module.
  • Real time is limited to mentor chat.WebSocket is used for the mentor conversation only; the live scoreboard is not pushed.
Product & scope
  • English only.There is no internationalisation layer in the frontend, although parts of the internal documentation are written in Vietnamese.
  • Judging remains human.The system detects disagreement between judges; it does not evaluate submissions, and there is no AI or automated scoring anywhere in the codebase.
  • Thin end-to-end coverage.471 backend tests against three Playwright specs — the browser-level suite is far behind the API-level one.
  • Built for one competition format.Track draw, milestone gates and finalist rules are specific to SEAL_RAG_2026; generic events fall back to a simpler path.
